# 出勤台サーバー: IdP の最小構成(MVP)の実装計画

> 2026-11-09 改訂: 実装(PR #1、ブランチ `feat/idp-mvp`)に合わせて書き直した。着手時の計画から変わった点は「計画からの変更点」にまとめた。現在の不変条件は `CLAUDE.md`、他サービス向けの契約は `Docs/authentication.md`、証明書の運用は `Docs/certificate-rotation.md` を正とする。

## Context

運転会の認証基盤を、出勤台サーバーへまとめる。出勤台サーバーを OIDC の IdP にし、Crew(MultiATS)・TTC(Rendo)・出勤台は、すべてここが発行したトークンで認証する。

ログイン・ログアウト・トークンの自動更新は出勤台クライアントにまとめ、他のアプリは、クライアントが書き出す DPAPI 暗号化のファイル(アクセストークンだけ)を読んでトークンを受け取る。

全体の計画と決定の経緯は、Rendo 側のメモ(`~/.claude/plans/public-private-serialized-rossum.md`、T0)にある。

Crew・TTC・各クライアントの移行は、この IdP が **prod で動いていること** を前提にしている。dev の IdP が発行したトークンは出勤台 dev でしか通らないため。そこで、IdP だけを先に作り、prod へデプロイする。

この計画の範囲は、IdP として最低限必要なものに絞る。勤怠や出勤台の機能(UC-02 以降)は、同じプロセスに後から足す。

## 決定事項

| 項目 | 決定 |
|---|---|
| 技術構成 | ASP.NET Core / **.NET 10** / OpenIddict 7.8.0 / EF Core 10 + Npgsql / PostgreSQL 16 / Discord.Net 3.20 |
| プロセス構成 | IdP と出勤台 API は1つのプロセスに同居させる |
| スキーマ管理 | Atlas。`Database/schema.sql` をあるべき状態として置き、`Database/migrations/` に diff を出す(Crew と同じ運用)。アプリは起動時にスキーマを作らない |
| issuer | prod は `https://shukkindai.example.invalid/`、dev は `https://shukkindai-dev.example.invalid/`。設定 `Authentication:Issuer` で固定する(末尾スラッシュ込みで完全一致。未設定・不正なら起動時に例外) |
| アクセストークン | JWS(RS256、`typ=at+jwt`)で、暗号化しない。寿命は1時間。aud は付けない |
| refresh token | 寿命は7日で、使うたびに延長する(OpenIddict 既定の rolling と sliding。再使用の猶予は既定の30秒)。暗号化は既定のまま |
| claim | `sub` は Discord ユーザー ID(固定。Crew の Hub が ulong に変換するため)。`name` は Discord のユーザー名。ユーザー由来の claim はこの2つだけで、ロールと社員番号は入れない |
| scope | openid は使わない(宣言も受付もしない。identity token を発行しないため)。通すのは `offline_access` だけ |
| PKCE | 必須で、S256 だけ(plain は受け付けない) |
| 発行の条件 | 現在の Discord サーバーのメンバーだけに発行する。**refresh のときにも確かめる**。入鋏ロールは IdP では見ない |
| Discord の判定 | Bot のギルドキャッシュだけで行う(REST にフォールバックしない)。Gateway 接続中・ギルドあり・`guild.IsConnected`・`guild.HasAllMembers` の4条件がそろわなければ `temporarily_unavailable`。起動時に30秒以内にそろわなければ、起動に失敗する(Discord が落ちていれば運転会ができないので、IdP ごと落ちてよい) |
| 失効 | revoke エンドポイント(RFC 7009)を用意する。管理者による一括失効は MVP には入れない |
| クライアント | public client を1つ(出勤台クライアント用)だけ登録する。リダイレクト先は固定のループバックポートを数個 |
| 証明書 | Development 以外では、署名・暗号化の証明書を出勤台が自動で作り、`cert/public/` に公開し、再起動のときに切り替え、古いものを消す(下記「証明書」) |
| 監視 | `OTEL_EXPORTER_OTLP_ENDPOINT` があるときだけ OpenTelemetry(metrics・tracing・ログ)を送る。証明書の状態はメトリクスと固定の EventId のログで知らせる |

## 計画からの変更点(実装中に決めたこと)
- **構造を Traincrew_MultiATS_Server に揃えた**: Discord は Repository 層に置き(`Repositories/Discord/DiscordRepository`)、判断は Service、HTTP の糊は Controller に分けた。着手時の `Discord/DiscordMemberLookup.cs` や `Certificates/CertificateStore.cs` は作っていない。
- **`DiscordIssuerParameterSupport` は移植しなかった**: OpenIddict 7.8.0 では Discord の設定が独自の discovery で iss の対応を宣言しているため、不要だった。
- **openid scope と PKCE plain をやめた**: identity token を発行しないのに openid を宣言すると、OpenIddict.Client 側が失敗するため。plain は既定で受け付けてしまうので明示的に外した。
- **証明書を自動ローテーションにした**: 「有効期限は2年なので注意を Docs に書く」だけの予定だったが、自動化した(下記「証明書」)。Crew と TTC は `cert/public/` を読み取り専用でマウントして検証する(同じホストの見込み)。
- **Discord の同意画面で拒否したら、クライアントに返す**: OpenIddict Client の `EnableErrorPassthrough()` で callback がエラーを受け取り、ログイン途中の Cookie に失敗の印を付けて authorize に戻し、authorize が `state` 付きの `access_denied` を返す。
- **他のアプリへのトークンの渡し方**: 名前付きパイプをやめ、DPAPI で暗号化したファイル(アクセストークンだけ)にした(`Docs/authentication.md`)。
- **Q-01-4(権限判定に使うロールの取得元)**: Discord 上の現在のロール(Bot のギルドキャッシュ)にした(D-12)。MVP の範囲外。

## ソリューション構成

トップを `Docs/`・`Server/`・`Client/`・`Common/` に分ける。ソリューションはルートに1つだけ置き、全プロジェクトを含める。

```
Tatehama_shukkindai/
├── global.json                          # .NET 10 SDK、Microsoft.Testing.Platform
├── Tatehama_shukkindai.slnx             # 全プロジェクトを含む(.NET 10 既定の slnx 形式)
├── Directory.Build.props                # 共通設定(Nullable、TreatWarningsAsErrors など)
├── .github/workflows/unitTest.yml       # UT の workflow(PR ごとに ubuntu-latest で実行)
├── Docs/                                # 要件定義・UC・plans/・authentication.md・certificate-rotation.md
├── Server/
│   ├── compose.yml                      # ローカル用 PostgreSQL(ポート 5434)
│   ├── Dockerfile                       # ビルドコンテキストはリポジトリのルート(Common/ を参照するため)
│   ├── tools/                           # gen-cert.cs・inspect-cert.cs(証明書の手作業用)
│   ├── Database/
│   │   ├── atlas.hcl
│   │   ├── schema.sql                   # OpenIddict 4テーブル
│   │   └── migrations/
│   ├── Tatehama.Shukkindai.Server/      # ASP.NET Core(IdP + 将来の出勤台 API)
│   ├── Tatehama.Shukkindai.Server.UT/   # xUnit v3 + Moq
│   └── Tatehama.Shukkindai.Server.IT/   # WebApplicationFactory + 実 DB
├── Client/                              # MVP では空。出勤台クライアントのタスクで作る
└── Common/                              # Server と Client で共有する型。MVP では空
```

- 名前空間は `Tatehama.Shukkindai.*` にする。リポジトリ名(`Tatehama_shukkindai`)とは表記が違うが、C# の慣習に合わせた。
- **ソリューションを1つにすることの注意点**
  - Client は Windows 専用(`net10.0-windows`)になる。Linux の CI や開発機でソリューション全体をビルドできるよう、Client 側の csproj に `EnableWindowsTargeting=true` を入れる。Client のテストを実行するのは Windows だけにする。
  - CI と Dockerfile は、ソリューションではなく `--project Server/...` でプロジェクトを指定してビルドする。
  - Dockerfile のビルドコンテキストはリポジトリのルートにする。`.dockerignore` で `Client/` と `Docs/` を除き、`Server/` と `Common/` だけをイメージに取り込む。
- **Server と Client で共有する型**(出勤台 API の DTO など): `Common/Tatehama.Shukkindai.Common/` に作る。Common は OS に依存しない `net10.0` にして、Server と Client の両方から参照できるようにする。MVP では作らない。
- **トークン共有ファイルの契約**(出勤台クライアントと、ATS などの他のアプリとのやり取り。形式は `Docs/authentication.md` の「他のアプリへのトークンの渡し方」)は、Server とは関係がないので Client 側に置く。

### OpenIddict Server
- エンドポイントは次の4つ。
  - `connect/authorize`(パススルー)
  - `connect/token`(パススルー)
  - `connect/revoke`
  - discovery と JWKS(既定のまま公開する)
- `AllowAuthorizationCodeFlow()`、`AllowRefreshTokenFlow()`、`RequireProofKeyForCodeExchange()`。code challenge の方式から plain を外す。
- `SetIssuer` で issuer を固定する。未設定・不正なら起動時に失敗させる。
- `DisableAccessTokenEncryption()`。
- 寿命はアクセストークン1時間、refresh token 7日。identity token は発行しない(openid scope を使わない)。
- 証明書: Development では開発用の証明書を使い、それ以外では `Authentication:CertificateDirectory`(Docker では `/app/cert`)の自動ローテーションの証明書を使う。

### AuthorizationController の処理
- **authorize**: Discord ログイン → callback でログイン途中の Cookie(`__Host-Shukkindai.Login`、10分)を発行 → authorize に戻る。その後、次の順に処理する。
  1. ログイン途中の Cookie を消す(1回だけ使う。残すと次の authorize が Discord ログインを飛ばし、アカウントを切り替えられない)。
  2. callback が付けた失敗の印があれば、そのエラー(Discord の同意画面での拒否なら `access_denied`)を `state` 付きでクライアントに返す。
  3. Bot で、現在のサーバーメンバーかどうかを確かめる。メンバーでなければ `access_denied`、同期できていなければ `temporarily_unavailable`。
  4. `sub`(Discord ID)と `name`(ユーザー名)を、宛先をアクセストークンにして設定する。scope は `offline_access` だけを通す。
  5. ログインの監査ログを出し、`IUserLoginObserver` を呼ぶ。
- **token(authorization_code grant)**: principal をそのまま SignIn する。
- **token(refresh_token grant)**: refresh token の principal を取り出し、その sub がまだサーバーのメンバーかを Bot で確かめる。メンバーでなければ `invalid_grant`、同期できていなければ `temporarily_unavailable`。メンバーなら、`name` を最新のユーザー名に更新してから SignIn する。
- それ以外のグラントタイプは `unsupported_grant_type`。異常系は早期 return にしている。

### 証明書
詳細は `Docs/certificate-rotation.md`(処理の流れ・手順書・アラートの設計)と `CLAUDE.md` の「証明書」節。要点:
- 用途ごとのディレクトリ(`server-signing`・`server-encryption`・`client-signing`・`client-encryption`)に pfx を置き、署名の公開鍵を `cert/public/*.cer` に公開する。Crew と TTC はこのディレクトリを読み取り専用でマウントし、kid で鍵を選んで検証する。
- 寿命2年。署名は残り150日で次の鍵を作って公開し、期限の60日前以降の再起動で切り替える。切り替えは再起動のときだけで、必要になったらログ(7105)とメトリクスで知らせる。
- 有効な署名証明書が無ければ起動を止める。初回の生成は `Authentication:AllowCertificateBootstrap=true` のときだけ(`cert/` のマウント漏れで黙って新しい鍵で起動するのを防ぐ)。
- 公開していない鍵では署名しない。使っている鍵は、pfx が消えても再起動まで `.cer` を残す。

### クライアントの登録
- 起動時に `Tatehama_Shukkindai_Client` を登録する。public client で、native として登録する。
- 権限: authorization・token・revocation の各エンドポイント、code フロー、refresh_token。PKCE は必須。
- リダイレクト URI は `http://localhost:{port}/` で、ポートは設定 `Authentication:ClientRedirectPorts` から読む(既定は 51180〜51184)。
- 既に登録済みの場合は、記述子を**更新する**。Crew は「登録済みなら何もしない」ので、権限を追加しても反映されなかった。

### 設定(appsettings / 環境変数)
- `Authentication:Issuer`、`Authentication:ClientRedirectPorts`、`Authentication:CertificateDirectory`、`Authentication:AllowCertificateBootstrap`
- `Discord:ClientId`、`Discord:ClientSecret`、`Discord:BotToken`、`Discord:GuildId`(全環境で必須。秘密情報は User Secrets か環境変数で渡し、appsettings には書かない)
- `ConnectionStrings:DefaultConnection`
- `OTEL_EXPORTER_OTLP_ENDPOINT`、`OTEL_SERVICE_NAME` など(任意)
- デプロイの際に人間が行うこと(詳細は `Docs/authentication.md`):
  - Discord のアプリに `{issuer}auth/callback` をリダイレクト URI として追加する。
  - Bot の Server Members Intent を有効にし、Bot をギルドに招待する(無効だと起動に失敗する)。
  - `atlas migrate apply` で DB に migrations を当てる。
  - 初回だけ `AllowCertificateBootstrap=true` で起動し、鍵ができたら外す。

## テスト

**UT**(`Server/Tatehama.Shukkindai.Server.UT`、DB なし。クラスは `XxxTest`、メソッドは `Method_Condition_Result`)
- `TokenService`: メンバーなら sub と name が設定され、宛先がアクセストークンになる。メンバーでなければ access_denied(refresh では invalid_grant)。同期できていなければ temporarily_unavailable。refresh では name が更新される。
- `DiscordRepository`: Login していない状態で `IsReady()==false`・`GetMember` が Unavailable。不正なトークンで例外。
- 設定の検証、外部ログインの失敗の印、Discord の登録(オフライン)。
- 証明書: `CertificateRotationPolicy`(作る・切り替える・消すの判断)、`CertificateService`(起動時の確認、ローテーション、pfx が消えたとき)、`CertificateRepository`(権限、原子的な書き込み、`public/` の同期)、ログの EventId とメトリクス。
- `IDiscordRepository` などは Moq で差し替える。

**IT**(`Server/Tatehama.Shukkindai.Server.IT`、実 DB)
- Discord の外部ログインをテスト用の認証 scheme に差し替え、Discord の Bot は `FakeDiscordRepository` にする。そのうえで、HttpClient で authorization code + PKCE のフローを一周させる。
- 確認すること:
  - アクセストークンが JWS である(ドットが2つ)
  - `iss` が設定値と一致する
  - ユーザー由来の claim が `sub` と `name` だけ(許可リスト)
  - 寿命は約1時間
  - refresh でトークンを再取得できる
  - revoke の後に refresh すると invalid_grant になる
  - メンバーから外した後に refresh すると invalid_grant になる
  - Discord の同意画面での拒否が `state` 付きの `access_denied` でクライアントに返る
  - PKCE plain と openid scope を受け付けない
- discovery の issuer と、JWKS の鍵が署名証明書と一致すること。
- 証明書の自動ローテーション(初回の生成の許可、`public/` に書けないときの起動停止、再起動直後に古い鍵を消さないこと など)、OpenTelemetry の有効判定、`/healthz` が HTTP ログに出ないこと、クライアントの登録の更新。
