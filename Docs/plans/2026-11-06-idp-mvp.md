# 出勤台サーバー: IdP の最小構成(MVP)の実装計画

## Context

運転会の認証基盤を、出勤台サーバーへまとめる。出勤台サーバーを OIDC の IdP にし、Crew(MultiATS)・TTC(Rendo)・出勤台は、すべてここが発行したトークンで認証する。

ログイン・ログアウト・トークンの自動更新は出勤台クライアントにまとめ、他のアプリは、クライアントが書き出す DPAPI 暗号化のファイル(アクセストークンだけ)を読んでトークンを受け取る。

全体の計画と決定の経緯は、Rendo 側のメモ(`~/.claude/plans/public-private-serialized-rossum.md`、T0)にある。

Crew・TTC・各クライアントの移行は、この IdP が **prod で動いていること** を前提にしている。dev の IdP が発行したトークンは出勤台 dev でしか通らないため。そこで、IdP だけを先に作り、prod へデプロイする。

この計画の範囲は、IdP として最低限必要なものに絞る。勤怠や出勤台の機能(UC-02 以降)は、同じプロセスに後から足す。

## 決定事項(2026-11-06)

| 項目 | 決定 |
|---|---|
| 技術構成 | ASP.NET Core / **.NET 10** / OpenIddict 7.x(着手時の最新安定版。2026-11 時点で 7.8.0)/ PostgreSQL / Discord.Net |
| プロセス構成 | IdP と出勤台 API は1つのプロセスに同居させる |
| スキーマ管理 | Atlas。`Database/schema.sql` をあるべき状態として置き、`Database/migrations/` に diff を出す(Crew と同じ運用) |
| issuer | prod は `https://shukkindai.example.invalid/`、dev は `https://shukkindai-dev.example.invalid/`。設定 `Authentication:Issuer` で固定する |
| アクセストークン | JWS で、暗号化しない。寿命は1時間。aud は付けない |
| refresh token | 寿命は7日で、使うたびに延長する(OpenIddict 既定の rolling と sliding)。暗号化は既定のまま |
| claim | `sub` は Discord ユーザー ID(固定。Crew の Hub が ulong に変換するため)。`name` は Discord のユーザー名。ロールと社員番号は入れない |
| 発行の条件 | 現在の Discord サーバーのメンバーだけに発行する。**refresh のときにも確かめる**。入鋏ロールは IdP では見ない |
| 失効 | revoke エンドポイント(RFC 7009)を用意する。管理者による一括失効は MVP には入れない |
| クライアント | public client を1つ(出勤台クライアント用)だけ登録する。PKCE を必須にする。リダイレクト先は固定のループバックポートを数個 |

## ソリューション構成

トップを `Docs/`・`Server/`・`Client/` の3つに分ける。ソリューションはルートに1つだけ置き、全プロジェクトを含める。

```
Tatehama_shukkindai/
├── global.json                          # .NET 10 SDK、Microsoft.Testing.Platform
├── Tatehama_shukkindai.slnx             # 全プロジェクトを含む(.NET 10 既定の slnx 形式)
├── Directory.Build.props                # 共通設定(Nullable、TreatWarningsAsErrors など)
├── Docs/                                # 既存(要件定義・UC)+ plans/ + authentication.md
├── Server/
│   ├── compose.yml                      # ローカル用 PostgreSQL
│   ├── Dockerfile                       # ビルドコンテキストはリポジトリのルート(Common/ を参照するため)
│   ├── Database/
│   │   ├── atlas.hcl
│   │   ├── schema.sql                   # OpenIddict 4テーブル(Crew の public schema.sql から流用)
│   │   └── migrations/
│   ├── Tatehama.Shukkindai.Server/      # ASP.NET Core(IdP + 将来の出勤台 API)
│   ├── Tatehama.Shukkindai.Server.UT/   # xUnit v3 + Moq
│   └── Tatehama.Shukkindai.Server.IT/   # WebApplicationFactory + 実 DB
├── Client/                              # MVP では空。出勤台クライアントのタスクで作る
└── Common/                              # Server と Client で共有する型。MVP では空
```

- 名前空間は `Tatehama.Shukkindai.*` にする。リポジトリ名(`Tatehama_shukkindai`)とは表記が違うが、C# の慣習に合わせた。
- **ソリューションを1つにすることの注意点**
  - Client は Windows 専用(`net10.0-windows`)になる。Linux の CI や開発機でソリューション全体をビルドできるよう、Client 側の csproj に `EnableWindowsTargeting=true` を入れる。Client のテストを実行するのは Windows だけにする。
  - CI と Dockerfile は、ソリューションではなく `--project Server/...` でプロジェクトを指定してビルドする。
  - Dockerfile のビルドコンテキストはリポジトリのルートにする。`.dockerignore` で `Client/` と `Docs/` を除き、`Server/` と `Common/` だけをイメージに取り込む。
- **Server と Client で共有する型**(出勤台 API の DTO など): `Common/Tatehama.Shukkindai.Common/` に作る。Common は OS に依存しない `net10.0` にして、Server と Client の両方から参照できるようにする。MVP では作らない。
- **トークン共有ファイルの契約**(出勤台クライアントと、ATS などの他のアプリとのやり取り。形式は `Docs/authentication.md` の「他のアプリへのトークンの渡し方」)は、Server とは関係がないので Client 側に置く。

## 実装(`Server/Tatehama.Shukkindai.Server`)

Crew の実装を移植元にする。移植元の場所は `Traincrew_MultiATS_Server` リポジトリ。

| 新しいファイル | 移植元 | 変更点 |
|---|---|---|
| `Program.cs` の OpenIddict Server 設定 | `Crew/Program.cs` `ConfigureOpeniddictService` | 下記「OpenIddict Server」を参照 |
| `Program.cs` の OpenIddict Client(Discord)設定 | `Crew/Program.cs` `ConfigureOpeniddictClientService` | scope は `identify` だけにする。ギルドの確認は Bot で行うので、`guilds` と `guilds.members.read` は不要 |
| `Authentication/DiscordIssuerParameterSupport.cs` | `Crew/Authentication/DiscordIssuerParameterSupport.cs` | そのまま。上流の修正 #2563 は 8.0 にしか入っていないため、7.x を使う間は必要 |
| `Controllers/AuthorizationController.cs` | `Crew/Controllers/AuthenticationController.cs` | authorize と callback に加えて、token のパススルーを処理する(下記) |
| `Discord/DiscordMemberLookup.cs`(`IDiscordMemberLookup`) | `Repositories/Discord/DiscordRepository.cs` と `DiscordBotHostedService` | 機能を「メンバーかどうか」と「ユーザー名」の取得に絞る。GatewayIntents は Guilds と GuildMembers |
| `Certificates/CertificateStore.cs` | `Crew/Program.cs` `EnsureCertificateExists` | 署名用の公開鍵を `.cer` でも書き出す(Crew と TTC が静的に検証するため)。有効期限は2年なので、ローテーションの際の注意を Docs に書く |
| `Program.cs` の `/healthz` | Crew と同じ | DB 接続と Bot の Ready を確認する |

### OpenIddict Server
- エンドポイントは次の4つ。
  - `connect/authorize`(パススルー)
  - `connect/token`(パススルー)
  - `connect/revoke`
  - discovery と JWKS(既定のまま公開する)
- `AllowAuthorizationCodeFlow()`、`AllowRefreshTokenFlow()`、`RequireProofKeyForCodeExchange()`。
- `SetIssuer(new Uri(config["Authentication:Issuer"]))` で issuer を固定する。未設定なら起動時に失敗させる。
- `DisableAccessTokenEncryption()`。
- 寿命はアクセストークン1時間、refresh token 7日。identity token は発行しない(openid scope を使わない)。
- 証明書: Development では開発用の証明書を使い、それ以外では `cert/` 配下の永続ファイルを使う(Crew と同じ方式)。

### AuthorizationController の処理
- **authorize**: Discord ログイン → callback で Cookie を発行 → authorize に戻る。その後、次の順に処理する。
  1. Bot で、現在のサーバーメンバーかどうかを確かめる。メンバーでなければ `access_denied` を返し、「Discord サーバーのメンバーではありません」と表示する。
  2. `sub`(Discord ID)と `name`(ユーザー名)を、宛先をアクセストークンにして設定する。scope は `offline_access` だけを通す。
  3. ログインの監査ログを出す(Crew の形式を引き継ぐ)。
  4. 将来 UC-02(社員番号の発番)を差し込むためのフックとして、`IUserLoginObserver` を用意する。MVP では何もしない実装にする。
- **token(refresh_token grant)**: refresh token の principal を取り出し、その sub がまだサーバーのメンバーかを Bot で確かめる。メンバーでなければ `invalid_grant` を返す。メンバーなら、`name` を最新のユーザー名に更新してから SignIn する。
- **token(authorization_code grant)**: principal をそのまま SignIn する。
- Bot が Discord と同期できていないとき(切断後の再接続中など)は `temporarily_unavailable` を返す。起動時に同期できなければ起動を失敗させる(`Docs/authentication.md` の運用上の注意を参照)。「メンバーではない」とは区別する。

### クライアントの登録
- 起動時に `Tatehama_Shukkindai_Client` を登録する。public client で、native として登録する。
- 権限: authorization・token・revocation の各エンドポイント、code フロー、refresh_token。PKCE は必須。
- リダイレクト URI は `http://localhost:{port}/` で、ポートは設定 `Authentication:ClientRedirectPorts` から読む(既定は5個程度)。
- 既に登録済みの場合は、記述子を**更新する**。Crew は「登録済みなら何もしない」ので、権限を追加しても反映されなかった。

### 設定(appsettings / 環境変数)
- `Authentication:Issuer`、`Authentication:ClientRedirectPorts`
- `Discord:ClientId`、`Discord:ClientSecret`、`Discord:BotToken`、`Discord:GuildId`
- `ConnectionStrings:DefaultConnection`
- Discord のアプリには、`{issuer}auth/callback` をリダイレクト URI として追加する必要がある。これはデプロイの際に人間が行う。

## DB(`Server/Database/`)
- `schema.sql`: OpenIddict の4テーブル(Applications / Authorizations / Scopes / Tokens)。Crew の `schema.sql` の定義を、7.x の列(`OpenIddictTokens.type` が varchar(150))に合わせて流用する。
- users テーブルは MVP では作らない。UC-02 と UC-04 の実装のときに追加する。
- `atlas.hcl` は Crew と同じ構成にする。dev 用 DB の URL は docker のものを使う。

## テスト

**UT**(`Server/Tatehama.Shukkindai.Server.UT`)
- authorize: メンバーなら sub と name が設定され、宛先がアクセストークンになる。メンバーでなければ access_denied。Bot が Ready でなければ temporarily_unavailable。
- token(refresh): サーバーを抜けていたら invalid_grant。メンバーなら name が更新される。
- クライアント登録: 新規なら作成する。既存なら更新する(権限とリダイレクト URI が反映される)。
- `IDiscordMemberLookup` は Moq で差し替える。

**IT**(`Server/Tatehama.Shukkindai.Server.IT`、実 DB)
- Discord の外部ログインをテスト用の認証 scheme に差し替える。そのうえで、HttpClient で authorization code + PKCE のフローを一周させる。
- 確認すること:
  - アクセストークンが JWS である(ドットが2つ)
  - `iss` が設定値と一致する
  - `sub` と `name` だけが入っている
  - 寿命は約1時間
  - refresh でトークンを再取得できる
  - revoke の後に refresh すると invalid_grant になる
  - メンバーから外した後に refresh すると invalid_grant になる
- discovery の issuer と、JWKS の鍵が署名証明書と一致すること。
