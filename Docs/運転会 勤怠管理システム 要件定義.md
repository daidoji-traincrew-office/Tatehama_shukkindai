# 運転会 勤怠管理システム 要件定義

## 用語集

| 用語 | 定義 |
| --- | --- |
| ダイヤ | その運転会で走らせる全列車の時刻表。列車番号ごとに発着時刻や折り返しが決まっている |
| 行路 | ダイヤを運転士1人分ずつに分けたもの。担当する列車を列車番号で指定する（例：新野崎発の各停で立浜へ行き、折り返しの新野崎行きも担当） |
| 出勤台 | 運転会1回分の、誰がどの行路・信号・司令の枠に入るかをまとめた表。1つの枠に見習いと指導員が一緒に入ることがある。将来は運転士＋車掌の2人乗務も想定する |
| 正業 | 見習いを卒業し、その役職を1人で担当できるようになった状態 |
| ログイン中 | デスクトップアプリが有効なアクセストークンを持っている状態 |
| 社員番号発番済み | 一度でもデスクトップアプリにログインし、社員番号が付いている状態。出勤台の枠に入れる・主催者に指定するなど、「その人がシステムを使える人か」を問う条件にはこちらを使う（その時点でログイン中かどうかは問わない） |
| Discordのユーザー名 | Discordのアカウントのユーザー名（例：tatehama_taro）。サーバー内のニックネームやグローバル名ではない。システムには保存せず、必要なときにDiscordから取得する。トークンの `name` と、表示名が未設定の人の代わりの表示に使う |
| 表示名 | 運転会での名義（例：館浜太郎）。Discordのユーザー名とは別に、運転会が独自に管理する。システム内の画面や通知で人を表すのに使う。初期値は入れず、運営だけが設定・変更できる（最初の設定を本人が行うかは UC-28 の Q-28-4 で検討中）。未設定の人は、Discordのユーザー名で代える |

## 目的

- 見習いの幽霊部員化を防ぐため、役職ごとに参加期限を管理する
- 現行の出勤台の機能を移行し、出勤記録の保存・集計を行う
- 既存の運転会システムとは完全に切り離して新規に作る

## 対象運転会

- A（体験版）・B（本格的な運転会）の両方で使う
- 見習い期限の最終参加日は、B運転会の実際の出勤記録でのみ更新する（Aへの参加は数えない）

## アクター

### Discordロール（何ができるかを示す）

乗務（運転士）系
- 見習い運転士（3ヶ月の期限あり）
- 運転士
- 指導運転士：見習い運転士を指導する
- 乗務主任：点呼と、運転会の実施中に起きた突発的な行路の組み換えを担当する
- 乗務助役：運転士・指導運転士を監督する。指導運転士が閲覧できる見習い運転士の情報も閲覧できる

信号系
- 見習い信号掛（3ヶ月の期限あり）
- 信号掛
- 駅助役：見習い信号掛を指導し、信号掛を監督する

司令系
- 司令員見習い
- 司令員
- 司令長見習い
- 司令長：司令員見習い・司令長見習いを指導し、司令員を監督する
- 司令系の見習いには期限を設けない

運営系
- ダイヤ部：デフォルトのダイヤ・行路（仕業）を編集する
- 運営補助：運営の操作の一部ができる（範囲は未決）
- 運営（管理者）：すべての権限を持ち、システム全体を管理する

### 運転会ごとの役割（ロールの範囲内から割り当てる）

- 運転士・信号掛・司令員：持っているロールの範囲内で、運転会ごとに担当を決める
- 主催者：司令長または司令長見習いのロールを持つ人がなり、運転会内では司令を務める。運転会の作成、運転会用の行路・ダイヤ・信号区割りの設定、途中離脱・途中参加の承認と書き換え、公開設定を担う
- 共同主催者：司令長または司令長見習いのロールを持つ人がなれる。主催者と同等の権限を持つ
- 指導員：運転会ごとに割り当て、見習い1人に指導員が1人つく
  - 見習い運転士には指導運転士、見習い信号掛には駅助役、司令員見習い・司令長見習いには司令長がつく
  - 1人の指導員が複数の見習いを同時に担当することも可能にする（実際はほぼない）
- 指導員として入った回も、そのロールの出勤記録・最終参加日として数える

## 権限

- Discordのロールを権限の基準とする
- 出勤台の枠に入れられるのは、社員番号発番済みで、かつその役職の見習いロールまたは正業ロールを持つ人のみ
- 正業への昇格は、指導員からの要望を受けて運営がDiscordロールを手で変更する
- デフォルトのダイヤ・行路を編集できるのはダイヤ部（と運営）のみ。運転会用のコピーは主催者・共同主催者が編集する
- 出勤記録の閲覧範囲
  - 本人：自分の記録のみ
  - 指導運転士：見習い運転士の記録
  - 乗務助役：運転士・指導運転士・見習い運転士の記録
  - 駅助役：信号掛・見習い信号掛の記録
  - 司令長：司令員・司令員見習い・司令長見習いの記録
  - 運営：すべての記録

## UI

- Discord Bot：通知とロールのチェックのみを担当する
- C#製のデスクトップアプリ：それ以外の操作（ダイヤ・行路・信号区割り・出勤台の編集、行路の希望、途中離脱・途中参加の申請と承認、記録の閲覧）はすべてここに集約する
  - 対応OSはWindowsのみ（Traincrew自体がWindows専用のため）
  - ログインはDiscord OAuth
  - アプリはDBに直接接続せず、APIサーバーを経由する。閲覧範囲の判定はAPI側で行う
  - GitHub Releasesで配布し、起動時に最新版を確認する。APIが対応する最低バージョンより古いアプリは出勤台APIを使えない（APIの呼び出しのたびに判定する）

## 社員番号

- システム内部ではDiscordのユーザーIDで人を識別し、社員番号は後から付く項目として扱う
- デスクトップアプリに初回ログインしたときに自動で発番する
- 同じ人が別のDiscordアカウントで入り直した場合は、発番の後に運営が2つのユーザーを統合する。番号は旧番を使い、新しく発番された番号は欠番にする
- 8桁：年3桁＋月2桁＋連番3桁（年月は初回ログインした年月）
- 番号は維持し、退会者の番号は再利用しない
- Discordサーバーを退会した人は、記録と社員番号を残して「退会済み」とし、期限管理の対象から外す。再入会した場合は以前の番号を使う

## 見習い期限

- 対象は見習い運転士と見習い信号掛のみ（司令系の見習いには期限を設けない）
- 最終参加日は役職ごとに記録する（例：運転士として最後に参加した日、信号掛として最後に参加した日）
- 「参加」とは、Bの出勤台の最終状態にその役職で載っていること。途中で抜けた人も、担当した部分があれば参加に数える
- 期限の起点は、その役職の最終参加日。まだ一度も参加していない場合は、見習いロールが付いた日
- 2.5ヶ月のリマインドはその日の12時（日本時間）に投稿する。時刻は定数として埋め込まず、運用中に変えられるようにする
- 日付は日本時間で数える。起点から暦の上で3ヶ月後の日に再スタートし、その15日前にリマインドする（例：最終参加が8月10日なら、リマインドは10月26日、再スタートは11月10日）。日付をまたぐ運転会は開始日を開催日とする
- 再スタート（自動で処理する）
  - 見習いの進捗は各指導員が管理し、システムでは管理しない
  - システムは、期限切れになった役職の見習いロールだけを外す（社員番号は維持）
  - 指導者用チャンネルと本人のDMに通知し、それを受けて指導員が進捗をリセットする
  - 見習いロールが付け直されたら、その日から新しく3ヶ月を数える
- 2.5ヶ月時点（再スタートの15日前）のリマインド
  - 見習い運転士の分は指導運転士向け、見習い信号掛の分は駅助役向け
  - 送り先は指導者用チャンネルにまとめて投稿
- ロールの変化の検知
  - Botはロールの付与・削除をその場で拾って記録する
  - Botの起動時に全メンバーのロールと突き合わせ、停止中に見逃した変化を拾い直す
  - 見習いロールと正業ロールを両方持っているなどの矛盾は、管理者に通知する

## 出勤台

### 行路・ダイヤ

- ダイヤは名前をつけて複数の種類を持てる
- 行路は「列車番号のリスト」として持ち、発着時刻は持たない（「何ダイヤの何列車を担当したか」が記録に残ればよい）
- 列車番号の検証で異常（ダイヤにない列車番号など）があっても、警告にとどめて保存できる（突発で列車が運転されることがあるため）
- デフォルトの行路・ダイヤを設定・編集できるのはダイヤ部（と運営）のみ
- 運転会を作るとき、デフォルトのダイヤと行路をその運転会用にコピーする。運転会ごとの変更はコピーにだけ加え、確定時にコピーごとアーカイブする（デフォルトを後から編集しても過去の記録は変わらない）
- 変更できるのは主催者と共同主催者

### 枠の割り当てと編集

- 見習いを指導員なしで枠に入れた場合は、警告を出す（保存はできる）
- 主催者と共同主催者が同時に編集した場合は、後から保存した人に警告して読み込み直させる（保存時にバージョンを照合する）

### 行路の希望と抽選

- 行路の希望を表明できる
- 人気行路は抽選する
- 抽選のタイミング（手動か締切時刻での自動か）：**保留**
- 公開設定（運転会ごとに主催者が決める）
  - 希望人数：デフォルトは非公開
  - 誰が希望したか：デフォルトは非公開
  - 当選者がどの行路に入ったか：**必ず公開**

### 途中離脱・途中参加

- 本人が申請して主催者が承認するルート
- 主催者が直接出勤台を書き換えるルート（急な離脱向け）
- 両方に対応する
- 途中離脱・途中参加・行路分割は、すべて「行路の中の列車ごとに担当者を記録する」1つの仕組みで表す（例：運転士Xが2列車目で抜け、Yが3列車目から引き継いだ場合、X：1〜2列車目、Y：3列車目〜最後）
- 途中で抜けた人も、担当した部分があれば参加として数える

### 行路分割

- 駅ではなく、行路内の途中の列車（ダイヤ）で区切る（頻度は低い）
- 分割した場合は担当者全員の最終参加日を更新する

### 最終状態の保存

- 出勤台の最終状態をアーカイブとして保存し、出勤記録の集計に使う
- 確定の仕方（誰が・いつ確定するか、確定後の修正、確定し忘れたときの扱い）：**保留**

## 信号・司令シフト

- 基本は運転会1回につき担当固定
- 長時間の運転会では時間帯で交代できるよう、開始・終了時刻つきの枠として持つ
- 途中離脱した人は、枠の終了時刻を早めて表す
- 信号掛は担当エリアごとに複数人（近い数駅のまとまりが多い。まれに全駅を1人で担当）
- 担当駅の区切り方は主催者が運転会ごとに自由に設定する

## 通知（Bot）

1. 2.5ヶ月のリマインド：指導者用チャンネルへ
2. 再スタートの実施：指導者用チャンネルと本人のDMへ
3. 途中離脱・途中参加の申請：主催者と共同主催者のDMへ
4. 申請の承認・却下の結果：本人のDMへ
5. ロールの矛盾：管理者へ
6. 運転会の告知：主催者・共同主催者がアプリのボタンで投稿する（運転会の作成で自動では投稿しない）

行路の当選結果を本人にDMで送るかは、抽選のタイミングが決まってから決める。

## 集計

- 人ごと・役職ごとの最終参加日・期限日・B運転会への参加回数の一覧（A運転会への参加は、別の列に回数だけ出す）
- 1人の出勤履歴（運転会、ダイヤ、担当した列車、または信号の区割り・時間帯）
- 運転会ごとの確定済み出勤台
- グラフや統計は後から追加する

## 他システムとの連携（制約）

- TTC（Rendo）が、運転会の開催日時とTST時差を出勤台から得る必要がある
  - 出勤台は、運転会ごとの開催日時とTST時差を持ち、TTCが取得できるようにすること
  - 実現方法（APIの形、TTCが取得するタイミング、TST時差を誰がどこで入力するか）：**保留**

## 非機能要件

- 記録は長期間保持し、消えないようにする
- DBは現在のサーバーと同じマシンに置く
- APIはCloudflareのDNS Proxy経由で公開し、サーバーマシンの既存のリバースプロキシを使う
- バックアップ
  - メイン：毎日1回DBダンプを取り、Oracleのオブジェクトストレージへ送る。30日分を残し、それより古いものは月1つだけ長く残す
  - 補助：出勤台を確定するたびに、Discordにダンプを投稿する（容量制限やチャンネル削除のリスクがあるため補助扱い）
  - 数ヶ月に一度、別の環境にダンプを戻して、復元できるかを確認する
- 個人情報保護法の対象になる情報は持たない見込み（表示名程度）

## 点呼のアルコール検査（全体を再検討中）

- 点呼のときに行うアルコール検査の結果を、サーバーを経由して点呼担当者（乗務主任）が確認できるようにする
- 検知したときは、点呼場所（列車区休憩所）にあたるDiscordのボイスチャンネルで、Botが検知音を鳴らす
- ごく低い確率で検知する演出と「酒飲んでますモード」（必ず検知される）は残す
- 細部（検査結果を出勤処理に影響させるか、記録として残すか、点呼の流れのどこで行うか、鳴らすボイスチャンネル）は UC-27 で検討する

- 行路の当選結果を本人にDMで通知するか（抽選のタイミングが決まってから決める）
