# UC-08 2.5ヶ月リマインドを指導者用チャンネルへ投稿する

## 概要
再スタート日の15日前（2.5ヶ月時点）を迎えた見習いを、指導者用チャンネルに1回の投稿でまとめて知らせる。運転士の見習いは指導運転士向け、信号扱者・指令員の見習いは輸送指導向けに分けて載せる。

## 主アクター
スケジューラ（時刻起動）

## 関係アクター
- Discord Bot（投稿を行う）
- 指導運転士、輸送指導（通知を受け取る）
- 事業本部（投稿が失敗したときに知らせる先。要判断事項 Q-08-5 参照）

## トリガー
毎日決まった時刻（日本時間）にスケジューラが起動する。実行時刻は要判断事項 Q-08-1 参照。

## 事前条件
- UC-07 で期限（リマインド日・再スタート日）を算出できる
- 指導者用チャンネルが設定されていて、Bot に投稿の権限がある

## 基本フロー
1. スケジューラが起動し、今日の日付（日本時間）を求める。
2. UC-07 の算出結果から、次の条件をすべて満たす「人×役職」を取り出す。
   - その役職の見習いロールを今も持っている
   - 退会済みでない
   - リマインド日が今日である。Bot の停止などで過ぎてしまった分の扱いは代替フロー A2 を参照
   - 同じ「人×役職×再スタート日」について、まだリマインドを送っていない
3. 取り出した対象を2つのグループに分ける。
   - 指導運転士向け：見習い運転士
   - 輸送指導向け：信号扱者見習い、指令員見習い
4. 指導者用チャンネルに、グループごとに見出しを付けて1回の投稿でまとめる。各行に載せる項目は次のとおり。
   - 名前（Discord の表示名。社員番号を載せるかは Q-08-3 参照）
   - 役職
   - 最終参加日（未参加なら「未参加（ロール付与日：YYYY/MM/DD）」）
   - 再スタート日
   - 宛先のロールにメンションするかは要判断事項 Q-08-2 参照
5. 投稿できたら、対象ごとにリマインド送信記録（人・役職・再スタート日・送信日時）を保存する。

## 代替フロー
- A1 対象がいない日：要判断事項 Q-08-4 参照。
- A2 Bot やスケジューラの停止でリマインド日を過ぎていた場合：再スタート日の前日までなら、次に起動したときに送る（未送信の記録がある分だけ）。再スタート日を過ぎていたらリマインドは送らず、UC-09 に任せる。
- A3 リマインドの後に、B運転会への参加が確定して起点が新しくなった場合：再スタート日が変わるので、新しい再スタート日に対してあらためてリマインドを送る（送信記録は再スタート日ごとに持つ）。取り消しの投稿はしない。
- A4 片方のグループだけに対象がいる場合：対象のいるグループの見出しだけを載せる。
- A5 投稿が Discord のメッセージの文字数上限を超える場合：グループごと、または一定の行数ごとに投稿を分ける。

## 例外フロー
- E1 指導者用チャンネルが見つからない、または投稿の権限がない場合：送信記録を保存しない（次に起動したときに送り直せるようにする）。エラーをログに残す。管理者に知らせるかは Q-08-5 参照。
- E2 Discord API のレート制限や一時的なエラーの場合：一定回数まで再試行する。それでも失敗したら E1 と同じ扱いにする。
- E3 投稿は成功したのに送信記録の保存に失敗した場合：次の起動時に二重に投稿されることがある。二重投稿は許容する（送り漏れよりも害が小さいため）。

## 事後条件
- 今日がリマインド日の対象（再送分を含む）が、指導者用チャンネルに1回投稿されている。
- 対象ごとにリマインド送信記録が保存されている。
- ロールや期限は変えない。

## 扱うデータ（エンティティと主な項目）
- 期限の算出結果（UC-07）：DiscordユーザーID、役職、最終参加日、起点の種別、リマインド日、再スタート日
- 人：DiscordユーザーID、表示名、社員番号、退会済みフラグ
- リマインド送信記録：DiscordユーザーID、役職、再スタート日、送信日時、DiscordメッセージID
- 設定：指導者用チャンネルID、実行時刻、指導運転士・輸送指導のロールID

## 通知
- 要件定義書の通知1「2.5ヶ月のリマインド：指導者用チャンネルへ」
- 本人への DM は要件定義書にない（DM で知らせるのは再スタートのときだけ）。

## 権限チェック
- システムが自動で行う処理なので、利用者の権限チェックはしない。
- 投稿先は指導者用チャンネルに固定する。そのチャンネルを誰が見られるかは Discord 側のチャンネル権限で管理する。

## 関連UC
- UC-07 役職ごとの最終参加日・期限日を算出する（対象の抽出元）
- UC-09 期限切れで見習いロールを外し再スタート通知する（このリマインドの後に起きる処理）
- UC-03 Discord退会/再入会を反映する（退会済みを除く）
- UC-21 出勤台を確定しアーカイブする（起点の更新元。確定方法は**保留**）
- UC-22 期限一覧を見る（リマインドの対象をアプリでも確認できる）

## 要件定義書の該当箇所
- 見習い期限（再スタートの15日前にリマインド、例：10/26）
- 見習い期限 > 2.5ヶ月時点のリマインド（運転士は指導運転士向け、信号・指令は輸送指導向け、指導者用チャンネルにまとめて投稿）
- 通知（Bot）> 1
- UI（Discord Bot は通知を担当する）

## 要判断事項
- **Q-08-1 毎日の実行時刻**
  - 選択肢1：日本時間の朝（例：9:00）
  - 選択肢2：日本時間の0:00過ぎ
  - 推奨：選択肢1。指導員が見やすい時間に届き、深夜の通知を避けられる。UC-09 と同じ時刻にそろえると運用が分かりやすい。
- **Q-08-2 指導者用チャンネルでのメンション**
  - 選択肢1：グループごとに指導運転士ロール・輸送指導ロールへメンションする
  - 選択肢2：メンションしない（投稿だけ）
  - 選択肢3：その見習いを担当している指導員にメンションする（ただし担当関係はシステムで管理していない）
  - 推奨：選択肢1。「運転士の見習い分は指導運転士向け」という宛先の区別を、確実に通知が届く形で表せる。選択肢3は担当関係のデータがないので実現できない。
- **Q-08-3 投稿に載せる本人の識別情報**
  - 選択肢1：本人へのメンション（ユーザーメンション）
  - 選択肢2：表示名と社員番号（メンションなし）
  - 推奨：選択肢2。本人に通知を飛ばさずに済む（リマインドは指導者向けのため）。社員番号があれば名前を変えた人も見分けられる。
- **Q-08-4 対象がいない日の投稿**
  - 選択肢1：投稿しない
  - 選択肢2：「本日の対象なし」と投稿する
  - 推奨：選択肢1。毎日の投稿がノイズになる。Bot が動いているかどうかの確認は別の手段で行う。
- **Q-08-5 投稿に失敗したときの管理者への連絡**
  - 選択肢1：ロールの矛盾の通知（UC-06）と同じ宛先で、管理者に知らせる
  - 選択肢2：ログに残すだけにする
  - 推奨：選択肢1。チャンネルの削除や権限の変更に気づかないままリマインドが止まるのを防げる。
