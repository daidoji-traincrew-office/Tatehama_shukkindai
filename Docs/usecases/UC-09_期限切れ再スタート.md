# UC-09 期限切れで見習いロールを外し再スタート通知する

## 概要
再スタート日を迎えた見習いについて、期限切れになった役職の見習いロールだけを自動で外す。そのことを指導者用チャンネルと本人の DM に知らせる。見習いの進捗のリセットは、通知を受けた指導員がシステムの外で行う。

## 主アクター
スケジューラ（時刻起動）

## 関係アクター
- Discord Bot（ロールの削除と通知を行う）
- 対象の見習い本人（DM を受け取る）
- 指導運転士、輸送指導（指導者用チャンネルで通知を受け取り、進捗をリセットする）
- 事業本部（失敗したときに知らせる先。要判断事項 Q-09-5 参照）

## トリガー
毎日決まった時刻（日本時間）にスケジューラが起動する。実行時刻と、再スタート日当日の参加をどう扱うかは要判断事項 Q-09-1 参照。

## 事前条件
- UC-07 で期限（再スタート日）を算出できる
- Bot が対象の見習いロールを外せる（Bot のロールが対象ロールより上位にあり、ロール管理の権限を持っている）
- 指導者用チャンネルが設定されている

## 基本フロー
1. スケジューラが起動し、今日の日付（日本時間）を求める。
2. UC-07 の算出結果から、次の条件をすべて満たす「人×役職」を取り出す。
   - その役職の見習いロールを今も持っている
   - 退会済みでない
   - 再スタート日が今日以前である（停止中に過ぎた分も含める）
   - ロールの矛盾（見習いと正業を両方持つ）がない（UC-07 Q-07-4 参照）
3. 実行の直前に、Discord 上で本人が今もその見習いロールを持っているかを確かめる。
4. 期限切れになった役職の見習いロールだけを外す。ほかの役職のロール、正業ロール、社員番号には触れない。
5. ロール履歴に削除を記録し、変更理由を「期限切れによる再スタート」とする。UC-04 はロール削除のイベントを拾うが、この記録と二重にならないようにする。
6. 再スタート記録（人・役職・起点・再スタート日・実施日時）を保存する。
7. 指導者用チャンネルに通知する。同じ実行回の対象は1回の投稿にまとめ、運転士分と信号・指令分に分けて載せる。各行には名前、役職、最終参加日（未参加ならロール付与日）、再スタート日を載せる。
8. 本人に DM で、期限切れでその役職の見習いロールを外したことと、指導員に連絡すれば見習いロールを付け直してもらえることを知らせる。文面の詳細は実装時に決める。

## 代替フロー
- A1 1人が複数の役職で同じ日に期限切れになった場合：役職ごとにロールを外す。本人への DM は1通にまとめる。
- A2 停止中に再スタート日を過ぎていた場合：次に起動したときに処理する。通知には本来の再スタート日を載せる。
- A3 その後に見習いロールが付け直された場合：UC-04 が付与日を記録し、UC-07 がその日から新しく3ヶ月を数える（このUCの処理対象ではない）。
- A4 対象がいない日：何も投稿しない（UC-08 Q-08-4 の判断に合わせる）。
- A5 対象者が、まだ確定していない今後の運転会の出勤台の枠に入っている場合：ロールを外すと、その枠に入れる条件を満たさなくなる。扱いは要判断事項 Q-09-3 参照。
- A6 再スタート日より前に開かれたB運転会の出勤台が、まだ確定していない場合：確定すれば起点が新しくなるかもしれない（確定方法は**保留**）。扱いは要判断事項 Q-09-2 参照。

## 例外フロー
- E1 ロールを外せなかった場合（権限が足りない、ロールの順位、Discord API のエラー）：一定回数まで再試行する。それでも失敗したら、その対象は再スタート記録も通知も行わず、次に起動したときに再び処理する。管理者への連絡は Q-09-5 参照。
- E2 手順3の確認で、本人がすでにその見習いロールを持っていなかった場合（手動で外された、昇格した）：処理しない。ロール履歴との食い違いは UC-05 の突き合わせで直す。
- E3 手順3の確認で、本人がすでにサーバーにいなかった場合：処理しない。UC-03 の退会処理に任せる。
- E4 本人に DM を送れない場合（DM を受け付けない設定など）：ロールを外したことは取り消さない。扱いは要判断事項 Q-09-4 参照。
- E5 指導者用チャンネルへの投稿に失敗した場合：ロールを外したことは取り消さない。投稿していない分として記録し、次に起動したときに再送する。

## 事後条件
- 対象の役職の見習いロールが Discord 上で外れている。
- ロール履歴（理由：期限切れ）と再スタート記録が保存されている。
- その役職は期限管理の対象から外れている。最終参加日、出勤記録、社員番号は残っている。
- 指導者用チャンネルと本人の DM に通知されている（失敗した分は再送待ちとして記録されている）。

## 扱うデータ（エンティティと主な項目）
- 期限の算出結果（UC-07）：DiscordユーザーID、役職、最終参加日、起点、再スタート日
- ロール履歴：DiscordユーザーID、ロール、削除、日時、変更理由（期限切れによる再スタート）
- 再スタート記録：DiscordユーザーID、役職、起点日、起点の種別、再スタート日、実施日時、ロール削除の結果、チャンネル通知の結果、DM の結果
- 人：DiscordユーザーID、表示名、社員番号、退会済みフラグ
- 設定：指導者用チャンネルID、実行時刻、役職と見習いロールIDの対応

## 通知
- 要件定義書の通知2「再スタートの実施：指導者用チャンネルと本人の DM へ」
- 失敗したときの管理者への連絡は Q-09-5 参照。

## 権限チェック
- システムが自動で行う処理なので、利用者の権限チェックはしない。
- 外せるのは見習いロールだけとする。正業ロール、指導ロール、事業本部ロールは外さないよう、外してよいロールを設定で限定する。
- Bot のロールには、見習いロールより上位であることとロール管理の権限が必要（運用で設定する）。

## 関連UC
- UC-07 役職ごとの最終参加日・期限日を算出する（対象の抽出元）
- UC-08 2.5ヶ月リマインドを指導者用チャンネルへ投稿する（このUCの15日前に起きる処理）
- UC-03 Discord退会/再入会を反映する
- UC-04 / UC-05 ロールの記録と突き合わせ（ロール削除・付け直しの記録）
- UC-06 ロールの矛盾を検知し管理者に通知する
- UC-17 出勤台の枠に人を割り当てる（ロールの条件）
- UC-21 出勤台を確定しアーカイブする（確定方法は**保留**）

## 要件定義書の該当箇所
- 見習い期限（起点から暦の上で3ヶ月後の日に再スタート、JST）
- 見習い期限 > 再スタート（自動で処理する、期限切れになった役職の見習いロールだけを外す、社員番号は維持、指導者用チャンネルと本人の DM、指導員が進捗をリセット、付け直したらその日から3ヶ月）
- 通知（Bot）> 2
- 権限（出勤台の枠に入れるのは見習いロールまたは正業ロールを持つ人のみ）
- 社員番号（退会済みは期限管理の対象外）

## 要判断事項
- **Q-09-1 再スタート日当日の扱いと実行時刻**
  例：起点8/10、再スタート日11/10。11/10当日にB運転会がある場合に参加できるか。
  - 選択肢1：再スタート日の日本時間の朝（例：9:00）に実行する。当日の参加では期限を延ばせない
  - 選択肢2：再スタート日は「最後に参加できる日」とし、その翌日に実行する
  - 推奨：選択肢1。要件定義書の「3ヶ月後の日に再スタートする」という文言にそのまま合う。UC-08 と同じ時刻にそろえられる。当日の運転会に出たい人には、リマインドから15日の猶予がある。
- **Q-09-2 再スタート日より前のB運転会が、まだ確定していない場合**（確定方法は**保留**）
  - 選択肢1：確定を待たずに予定どおりロールを外す（後で確定したら UC-07 Q-07-5 に従う）
  - 選択肢2：対象者がその運転会の出勤台に載っていれば、確定するまで再スタートを保留する
  - 推奨：選択肢2。実際には参加しているのにロールを外してしまう事故を防げる。ただし確定方法が決まるまでは仮の判断とする。
- **Q-09-3 確定前の出勤台の枠に入っている人がロールを外された場合**
  - 選択肢1：枠には残し、主催者・共同主催者が次に出勤台を開いたときに警告する
  - 選択肢2：枠から自動で外す
  - 推奨：選択肢1。出勤台の編集は主催者の判断に任せる範囲で、自動で書き換えると意図しない変更になる。
- **Q-09-4 本人に DM を送れなかった場合**
  - 選択肢1：指導者用チャンネルの投稿に「DM を送れなかった」と添え、指導員から本人に伝えてもらう
  - 選択肢2：ログに残すだけにする
  - 推奨：選択肢1。本人がロールを外されたことに気づかないままになるのを防げる。
- **Q-09-5 ロールの削除や通知に失敗したときの管理者への連絡**
  - 選択肢1：ロールの矛盾の通知（UC-06）と同じ宛先で、管理者に知らせる
  - 選択肢2：ログに残すだけにする
  - 推奨：選択肢1。Bot のロールの順位や権限が変わって処理が止まり続けるのを防げる。UC-08 Q-08-5 とそろえる。
- **Q-09-6 再スタートの前に管理者の確認を挟むか**
  - 選択肢1：確認なしで自動実行する
  - 選択肢2：対象を管理者に一覧で示し、承認されてから実行する
  - 推奨：選択肢1。要件定義書で「自動で処理する」と明記されている。誤りを防ぐ手段としては、15日前のリマインドと Q-09-2 で足りる。
