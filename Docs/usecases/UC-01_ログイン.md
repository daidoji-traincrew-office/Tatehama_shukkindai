# UC-01 デスクトップアプリへログインする

## 概要
利用者がC#製デスクトップアプリを起動し、最新版を確認したうえでDiscord OAuthでログインする。出勤台サーバーはOIDCのIdPとして、利用者が誰かとDiscordサーバーのメンバーであることを確認し、以降のAPI呼び出しに使うトークンを発行する。アプリのバージョンが最低対応バージョン以上であることは、ログイン時ではなく、出勤台APIの呼び出しのたびに確認する。初回ログインのときは社員番号の発番（UC-02）を起動する。

## 主アクター
- 利用者（Discordサーバーのメンバー全員。見習い/正業、指導運転士、輸送指導、主催者、共同主催者、事業本部）

## 関係アクター
- Discord（OAuth認可サーバー。メンバー確認にはBotを使う）
- GitHub Releases（最新版の配布元）
- 出勤台サーバー（IdPと出勤台APIを兼ねる）
- 他のアプリ（ATSなど。アプリからトークンを受け取る）

## トリガー
- 利用者がデスクトップアプリを起動する、またはログアウト後にログインを選ぶ

## 事前条件
- Windows環境にアプリがインストールされている
- 利用者がDiscordアカウントを持っている
- 出勤台サーバーに最低対応バージョンが設定されている

## 基本フロー
1. 利用者がアプリを起動する。
2. アプリがGitHub Releasesで最新版を確認する。
3. 起動中のアプリが最新版である。
4. アプリが出勤台サーバーの認可画面をブラウザで開く。出勤台サーバーが利用者をDiscord OAuthの認可画面へ送り、利用者が認可する（Discord OAuthは出勤台サーバーが仲介する）。
5. 出勤台サーバーがDiscordから利用者のDiscordユーザーIDを取得する。
6. 出勤台サーバーが、Botで利用者がDiscordサーバーのメンバーであることを確認し、Discordのユーザー名を取得する（要判断事項 Q-01-1 参照）。
7. 出勤台サーバーがDiscordユーザーIDで利用者を特定する。
   - 社員番号が未発番の場合は、UC-02を実行する。
8. 出勤台サーバーが、Botで利用者の現在のDiscordロールを取得する（要判断事項 Q-01-4 参照。ロールはトークンに含めない）。
9. 出勤台サーバーがアプリ用のトークンを発行し、アプリに返す（保持方法と有効期限は要判断事項 Q-01-3 参照）。トークンの `sub` はDiscordユーザーID、`name` はDiscordのユーザー名である。`name` は、出勤台で表示する名前（Q-01-5）とは別のものである。
10. アプリが出勤台APIを呼び出す。このときアプリのバージョンも送る。出勤台APIは、アプリのバージョンが最低対応バージョン以上であることを、呼び出しのたびに確認する。
11. アプリがホーム画面を表示する。画面には社員番号・表示名と、ロールに応じて使える機能を出す。
12. ATSなど他のアプリがトークンを必要とするときは、アプリがアクセストークンだけをDPAPIで暗号化したファイルに書き出し、他のアプリがそれを読む(形式は `Docs/authentication.md` 参照)。他のアプリは自分ではログインせず、refresh tokenも持たない。

## 代替フロー
- A1（手順3）新しい版がある場合：アプリが利用者に更新を案内する（案内の仕方は要判断事項 Q-01-2 参照）。現在の版が最低対応バージョン以上であれば、更新しなくてもログインを続けられる。
- A2（手順4）有効なトークンが保存されている場合：OAuthを省略し、保存済みのトークンで手順10〜11を行う。アクセストークンの期限が切れていれば、refresh tokenで更新する。更新のたびに、出勤台サーバーがDiscordサーバーのメンバーかを確かめる（Q-01-3 参照）。
- A3（手順7）表示名が前回から変わっている場合：保存している表示名を更新する（Q-01-5 参照）。

## 例外フロー
- E1（手順2）最新版を確認できない場合（GitHubに接続できないなど）：確認を飛ばして手順4へ進む。古すぎる版は手順10で弾く。
- E2（手順4）利用者が認可を拒否するか、認可画面を閉じた場合：ログインを中止し、ログイン画面に戻す。
- E3（手順10）最低対応バージョンより古い場合：出勤台APIの呼び出しを拒否し、更新が必要であることと配布先を示す。
- E4（手順6）Discordサーバーのメンバーでない場合（未参加・退会済みを含む）：ログインを拒否する（Q-01-1 参照）。refresh tokenでの更新時にメンバーでなくなっていた場合も、更新を拒否し、再ログインを求める。
- E5（手順4〜10）出勤台サーバーに接続できない場合：エラーを表示し、再試行できるようにする。Botの準備ができていないときは、メンバーでないとは区別して、しばらくしてからの再試行を案内する。

## 事後条件
- 成功時：利用者はログイン済みとなり、出勤台の枠に入れられる対象になる（要件定義書「権限」）。社員番号が発番済みである。
- 失敗時：トークンは発行されず、データも変わらない。

## 扱うデータ
- ユーザー：DiscordユーザーID（識別キー）、表示名、社員番号、在籍状態（在籍／退会済み）、初回ログイン日時、最終ログイン日時
- 認証セッション：出勤台サーバーが発行するトークン（アクセストークン1時間、refresh token 7日）。発行日時と有効期限を持つ。アプリのバージョンはログイン時には記録せず、出勤台APIの呼び出しのたびに判定する
- システム設定：最低対応アプリバージョン

## 通知
- なし（Botの通知対象外）

## 権限チェック
- アプリのバージョンが最低対応バージョン以上であること（出勤台API側で、呼び出しのたびに判定する）
- Discordサーバーのメンバーであること（Q-01-1。トークンの発行時とrefresh時に確かめる）
- ログインした後の各操作の権限と閲覧範囲は、各UCでAPI側が判定する（アプリ側の表示制御は補助にとどめる）

## 関連UC
- UC-02 社員番号を自動発番する（初回ログイン時に起動する）
- UC-03 Discord退会/再入会を反映する（退会済みの人はログインできない）
- UC-04 / UC-05 ロールの記録（期限の起点などに使う。権限判定には使わない。Q-01-4 参照）
- UC-17 出勤台の枠に人を割り当てる（ログイン済みであることが枠に入れる条件）

## 要件定義書の該当箇所
- 「UI」：C#製デスクトップアプリ、Windowsのみ、Discord OAuth、APIサーバー経由、GitHub Releasesでの配布、最低バージョン
- 「権限」：出勤台の枠に入れられるのはデスクトップアプリにログイン済みの人のみ
- 「社員番号」：初回ログイン時に自動発番

## 要判断事項
- Q-01-1 Discordサーバーのメンバーでない人（未参加・退会済み）のログインをどう扱うか
  - 選択肢：(a) ログインを拒否する／(b) ログインは許可し、自分の記録の閲覧だけにする／(c) 未参加は拒否し、退会済みだけ自分の記録を閲覧できるようにする
  - 決定：(a)（D-9）。未参加・退会済みのどちらもログインを拒否する。退会済みの人の記録の閲覧は管理者が対応する。
- Q-01-2 新しい版があるときの案内の仕方
  - 選択肢：(a) 通知してダウンロードページを開くだけ／(b) アプリが自動でダウンロード・更新する
  - 推奨：(a)。最低バージョンの判定で強制できるので、まずは実装の軽い方法でよい。自動更新は後から足せる。
- Q-01-3 ログイン状態の保持
  - 選択肢：(a) 起動するたびにOAuthを行う／(b) 出勤台サーバーが発行したトークンをローカルに保存し、期限内はOAuthを省略する
  - 決定：(b)。出勤台サーバーがOIDCのIdPとしてトークンを発行する。アクセストークンは1時間、refresh tokenは7日で、使うたびに延長する。refreshのたびに、Discordサーバーのメンバーかを確かめる。
- Q-01-4 権限判定に使うロールの取得元
  - 選択肢：(a) Botが記録したDB上のロール（UC-04/05）／(b) ログイン時にDiscord APIから直接取得する
  - 決定：(b)（D-12）。Discord上の現在のロールで権限を判定する。取得はBotのギルドキャッシュから行う（メンバー判定と同じ。REST APIにはフォールバックしない）。DBのロール保有履歴は権限判定に使わない。取るタイミング（ログイン時か、出勤台APIの呼び出しのたびか）は出勤台APIの設計のときに決める。
- Q-01-5 表示名（ハンドルネーム）として何を保存し、いつ更新するか
  - 選択肢：(a) サーバー内のニックネームを優先し、ログインのたびに更新する／(b) Discordのグローバル表示名をログインのたびに更新する／(c) Botがニックネームの変更を検知するたびに更新する
  - 推奨：(a)とBotによる検知の併用。出勤台ではサーバー内の呼び名が使われる想定のため。一度もログインしていない人も出勤台や一覧に名前で出したい。
