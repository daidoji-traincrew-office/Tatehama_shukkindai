# UC-21 出勤台を確定しアーカイブする

## 概要
運転会の出勤台の最終状態を確定し、運転会用のダイヤ・行路のコピーごとアーカイブとして保存する。アーカイブから出勤記録を作り、B運転会の場合は役職ごとの最終参加日を更新する（UC-07）。確定のたびに、補助バックアップとしてDBダンプをDiscordに投稿する。

**保留**：確定の仕方（誰が・いつ確定するか、確定後の修正、確定し忘れたときの扱い）。本書では確定が行われたときの処理内容（アーカイブの中身と確定後の処理）だけを記述する。

## 主アクター
**保留**（誰が確定するかは未決）

## 関係アクター
- APIサーバー（アーカイブ作成、出勤記録の作成、最終参加日の更新）
- Discord Bot（ダンプの投稿）
- 出勤台に載っている全員（記録の対象）

## トリガー
出勤台の確定（誰が・いつ行うかは **保留**）

## 事前条件
- 運転会が作成済みで、出勤台が未確定である
- 未処理の申請の扱いは要判断事項 Q-21-1 参照

## 基本フロー
1. 確定が開始される（開始の方法は保留）。
2. APIが確定前の確認を行い、問題があれば一覧にして返す（いずれも警告で、確定は止めない。Q-21-1 を除く）。
   - 担当者のいない列車（UC-20 Q-20-2）
   - 指導員のいない見習い
   - 確定時点でロールを失っている担当者（UC-17 Q-17-7）
3. APIが1つのトランザクションで次を行う。
   1. 出勤台アーカイブを作る（中身は「扱うデータ」参照）。運転会用のダイヤ・行路はコピーごと保存し、以後デフォルトや運転会用データを編集してもアーカイブは変わらない。
   2. アーカイブから出勤記録を作る。1人×1役職×1運転会ごとに1件とし、担当した列車または時間帯を持つ。
      - 行路：1列車以上の乗務割当がある人。途中で抜けた人・行路分割の担当者も、担当した部分があれば含む
      - シフト：1つ以上のシフト割当がある人
      - 指導員として入った人も含める（どの役職で数えるかは要判断事項 Q-21-2 参照）
   3. B運転会の場合、出勤記録の各人・各役職について最終参加日を開催日で更新する（UC-07。開催日は開始日の日本時間の日付）。既存の最終参加日のほうが新しい場合は変えない。A運転会の場合は更新しない。
   4. 出勤台を確定済みにし、以後の編集（UC-17〜UC-20）・申請（UC-18）・抽選（UC-16）・希望（UC-15）を受け付けなくする。
4. トランザクションが成功したら、APIが Bot にダンプの投稿を依頼し、Bot がDiscordにDBダンプを投稿する（範囲・投稿先は要判断事項 Q-21-3 参照）。
5. 確定の結果（警告の一覧を含む）を返す。

## 代替フロー
- A1 A運転会の確定：手順3-3を行わない。出勤記録は作り、A運転会への参加回数として集計される（UC-22）。
- A2 担当者が1人もいない運転会：アーカイブと確定は行い、出勤記録は0件になる。
- A3 確定後の修正：**保留**
- A4 確定し忘れたとき：**保留**

## 例外フロー
- E1 既に確定済み：APIは拒否する。
- E2 トランザクション中のエラー：全体を取り消し、出勤台は未確定のまま残す。
- E3 Discordへのダンプ投稿の失敗：確定は取り消さない（ダンプは補助バックアップのため）。失敗をログに残す。管理者に知らせるかは要判断事項 Q-21-4 参照。
- E4 編集中の主催者がいる：確定後にその人が保存すると、確定済みとしてAPIが拒否する。

## 事後条件
- 出勤台アーカイブが保存され、出勤台は確定済みで編集できない
- 出勤記録が作られている
- B運転会の場合、担当者全員の役職ごとの最終参加日が更新されている（期限日の再計算は UC-07）
- Discordにダンプが投稿されている（失敗時はログが残っている）

## 扱うデータ（エンティティと主な項目）
- 出勤台アーカイブ：ID、運転会ID、確定日時、確定者（保留）、確定時の出勤台バージョン番号、以下のスナップショット
  - 運転会：名前、種別（A/B）、開始日時、終了日時、開催日、主催者・共同主催者
  - 運転会用ダイヤ・行路（コピー）：ダイヤ名、行路の識別子、列車番号の順序付きリスト
  - 乗務割当：行路、列車、ポジション、担当者、立場（本務／見習い／指導）、指導対象
  - 信号区割り、シフト枠（種別・区割り・開始・終了時刻）、シフト割当（担当者・立場・指導対象）
  - 担当者ごとの確定時点の情報：DiscordユーザーID、社員番号、表示名
- 出勤記録：ID、出勤台アーカイブID、DiscordユーザーID、役職（運転士／信号扱者／指令員）、立場（本務／見習い／指導）、A/B、開催日、担当内容（ダイヤ名と担当した列車番号の一覧、または区割りと時間帯）
- 最終参加日（UC-07 が保持）：DiscordユーザーID、役職、最終参加日
- ダンプ投稿記録：出勤台アーカイブID、投稿日時、成否、ファイル名

## 要件定義書の該当箇所
- 出勤台「最終状態の保存」（アーカイブ、確定の仕方は保留）
- 出勤台「行路・ダイヤ」（確定時にコピーごとアーカイブ）
- 出勤台「途中離脱・途中参加」「行路分割」（担当した部分があれば参加、分割時は担当者全員の最終参加日を更新）
- 対象運転会（最終参加日はBの出勤記録でのみ更新）
- 見習い期限（参加の定義、開催日は開始日）
- アクター（指導員として入った回もそのロールの出勤記録・最終参加日として数える）
- 集計（運転会ごとの確定済み出勤台、1人の出勤履歴）
- 非機能要件「バックアップ」（確定のたびにDiscordへダンプ投稿）
- 未決事項

## 要判断事項
- **Q-21-1 確定時に「申請中」の申請が残っている場合**
  - A：確定できない（先に UC-19 で処理させる）
  - B：警告して確定できる。残った申請は自動で却下し、本人にDMで知らせる
  - 推奨：A。申請は出勤台の最終状態に影響するため、処理しないまま確定すると記録が実態と食い違う。確定の仕方自体が保留のため、自動確定を採る場合は改めて検討する。
- **Q-21-2 指導員として入った回をどの役職で数えるか**（要件定義書「そのロールの出勤記録・最終参加日として数える」の「そのロール」の解釈）
  - A：枠の役職（例：指導運転士として入った行路は「運転士」）で数える
  - B：指導員ロール（指導運転士／輸送指導）として数える
  - C：出勤記録は「役職＝枠の役職、立場＝指導」で1件持ち、集計で両方の見方を出せるようにする。最終参加日は枠の役職で更新する
  - 推奨：C。データを1通りに持ちながら、指導員としての出勤回数も後から集計できる。
- **Q-21-3 Discordに投稿するダンプの範囲と投稿先**
  - A：DB全体のダンプ（圧縮）を、管理者用の専用チャンネルに投稿する
  - B：確定した運転会のアーカイブだけ（JSON等）を投稿する
  - 推奨：A。要件定義書は「ダンプ」としており、補助バックアップとして単独で復元できるほうが役に立つ。データ量は小さい見込み。ファイルサイズの上限を超える場合は分割するか投稿を諦めてログに残す（メインのバックアップは UC-25）。投稿先チャンネルは管理者だけが見られる場所にする。
- **Q-21-4 ダンプ投稿に失敗したとき管理者に知らせるか**
  - A：ログに残すだけ
  - B：管理者に通知する
  - 推奨：B。補助とはいえ失敗が続くと気づけない。ただし要件定義書の通知一覧への追加になる。
