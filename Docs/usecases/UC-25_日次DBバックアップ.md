# UC-25 日次DBバックアップ

## 概要
毎日1回DBのダンプを取り、Oracleのオブジェクトストレージへ送る。30日分を残し、それより古いものは月1つだけ長く残す。記録を長期間消さずに保持するためのメインのバックアップ。

## 主アクター
- スケジューラ（時刻起動）

## 関係アクター
- DB（APIサーバーと同じマシン上）
- Oracleのオブジェクトストレージ
- 事業本部（管理者）：失敗時の対応（通知方法は 要判断事項 Q-25-4 参照）

## トリガー
毎日決まった時刻（日本時間。時刻は 要判断事項 Q-25-1 参照）。

## 事前条件
- サーバーマシンでDBが稼働している
- オブジェクトストレージへの書き込み用の認証情報がサーバーマシンに設定されている

## 基本フロー
1. スケジューラが規定時刻にバックアップ処理を起動する。
2. DBのダンプを取得する（稼働中のまま、整合性のあるダンプを取る）。
3. ダンプを圧縮する（暗号化するかは 要判断事項 Q-25-3 参照）。
4. 日付入りのファイル名でオブジェクトストレージへアップロードする。
5. アップロードの成功を確認する（サイズ・ハッシュの照合など）。
6. 保持ルールを適用する。
   - 直近30日分は残す
   - 30日より古いものは、月ごとに1つだけ残し、それ以外を削除する（どれを残すか・何年残すかは 要判断事項 Q-25-2 参照）
7. サーバーマシン上の一時ダンプファイルを削除する。
8. 実行結果をログに残す。

## 代替フロー
- A1 アップロードの一時的な失敗：一定回数・間隔をおいて再試行する。成功すれば通常どおり手順6へ進む。

## 例外フロー
- E1 ダンプ取得の失敗（DB停止など）：処理を中止し、ログに残して管理者に知らせる（Q-25-4）。
- E2 再試行してもアップロードに失敗：一時ダンプは消さずに残し、管理者に知らせる（Q-25-4）。保持ルールの適用（削除）は行わない。
- E3 保持ルール適用中の失敗：アップロード済みのバックアップはそのまま残し、ログに残す。次回実行時に再度適用する。
- E4 サーバーマシンの空き容量不足：処理を中止し、管理者に知らせる。

## 事後条件
- 成功時：当日分のダンプがオブジェクトストレージにあり、保持ルールどおりに古いものが整理されている。
- 失敗時：既存のバックアップは削除されずに残っている。

## 扱うデータ（エンティティと主な項目）
| 対象 | 主な項目 |
| --- | --- |
| DBダンプ | DB全体（アプリのデータを含む） |
| バックアップオブジェクト | ファイル名（取得日時入り）、サイズ、ハッシュ、取得日 |
| 実行ログ | 実行日時、結果（成功／失敗）、失敗理由 |

## 通知
要件定義書の通知（Bot）一覧にバックアップ関係の通知はない。失敗時の知らせ方は 要判断事項 Q-25-4 参照。

## 権限チェック
- ユーザー操作はない。オブジェクトストレージの認証情報はサーバーマシン上でのみ保持し、デスクトップアプリやDiscordには出さない。

## 関連UC
- UC-21 出勤台を確定しアーカイブする（確定ごとのDiscordへのダンプ投稿＝補助バックアップは UC-21 で扱う）
- UC-26 復元テスト（本UCで取ったダンプを使う）

## 要件定義書の該当箇所
- 非機能要件 > バックアップ > メイン：「毎日1回DBダンプを取り、Oracleのオブジェクトストレージへ送る。30日分を残し、それより古いものは月1つだけ長く残す」
- 非機能要件：「記録は長期間保持し、消えないようにする」「DBは現在のサーバーと同じマシンに置く」

## 要判断事項
- **Q-25-1 実行時刻**
  - 選択肢：(a) 深夜帯の固定時刻（例：日本時間4時）／(b) 運転会の開催時間帯を避けて都度調整
  - 推奨：(a)。固定時刻の方が運用・監視が単純。日付をまたぐ運転会もあるため、開催が終わっている可能性が高い早朝にする（開催時間帯の実態は要確認）。
- **Q-25-2 月ごとに長く残す1つの選び方と保持期間**
  - 選択肢：(a) 各月の最初の日のダンプを無期限に残す／(b) 各月の最後の日のダンプを無期限に残す／(c) (a)または(b)を一定年数（例：3年）残す
  - 推奨：(a)を無期限。記録を長期間消さない方針に合い、ダンプは小さい見込みで容量の負担も小さい。
- **Q-25-3 ダンプを暗号化するか**
  - 選択肢：(a) 暗号化しない（ストレージ側のアクセス制御のみ）／(b) アップロード前に暗号化する
  - 推奨：(a)。個人情報保護法の対象となる情報は持たない見込み（ハンドルネーム程度）。ただし鍵の管理が負担でなければ(b)も可。
- **Q-25-4 失敗時の知らせ方**
  - 選択肢：(a) Botで管理者へ通知する（通知一覧に追加）／(b) サーバーのログのみ（管理者が定期確認）／(c) 外部の死活監視サービスで検知する
  - 推奨：(a)。既存のBot通知の仕組みに乗せられ、気づかないまま30日分が失われる事態を防げる。
- **Q-25-5 保持ルールの実装方法**
  - 選択肢：(a) オブジェクトストレージのライフサイクルポリシーで管理（月次分は別の場所にコピー）／(b) バックアップスクリプトが削除まで行う
  - 推奨：(b)。「30日＋月1つ」はライフサイクルポリシーだけでは表しにくく、スクリプトで扱う方が分かりやすい。
